# 콘텐츠 생성 규칙

> 가이드 §5 기반. 슬라이드·노트 콘텐츠 생성 시 참조한다.
> **적용 범위**: LLM이 자체 생성하는 텍스트. 사용자가 직접 제공한 아웃라인·본문은 변경하지 않는다.

---

## 1. 한 슬라이드 = 한 메시지 (§5.1)

각 슬라이드는 두 테스트를 통과해야 한다.

| 테스트 | 기준 | 실패 시 |
|--------|------|---------|
| **25단어 테스트** | 핵심 메시지를 한글 50자/영문 70자 이내 한 문장으로 요약 가능한가? | 슬라이드 분할 |
| **Blink 테스트** | 0.5초 보여줬을 때 "어디가 주인공인지" 한 곳을 지목할 수 있는가? | 시각 계층 재설계 |

---

## 2. 제목 규칙 — 결론형 (§5.2)

제목은 **주제(topic)가 아니라 결론(takeaway)**.

| Bad (주제형) | Good (결론형) |
|-------------|--------------|
| "성능 벤치마크" | "콜드 스타트 지연을 73% 줄였다" |
| "아키텍처 개요" | "한 개의 데이터 경로가 세 개를 대체한다" |
| "고객 사례" | "A사는 도입 6개월 만에 인프라 비용 40% 절감" |
| "Q3 로드맵" | "Q3에 SDK 1.0을 공개한다" |
| "결론" | "파일럿을 이번 분기에 시작할 것을 제안한다" |

- 제목 길이: **한글 50자 이하**, 영문 70자 이하
- 수치가 포함된 제목이 기억률이 높다 — 가능하면 수치 포함

---

## 3. 본문 규칙 — 키워드 단위 (§5.3)

- 완전 문장(주어+서술어) 금지
- 글머리표 **최대 4개**. 초과 시 슬라이드 분할 또는 상위 범주 그룹화
- 글머리표 하나는 **한 줄** (한글 40자, 영문 60자 이하)
- 글머리표 간 **병렬 구조** (명사구끼리, 동사구끼리 통일)

**압축 예시**

Bad:
- 당사의 솔루션은 클라우드 네이티브 환경에서 마이크로서비스 아키텍처를 지원하며 확장성과 안정성을 제공합니다.

Good:
- 쿠버네티스 네이티브, 멀티리전 자동 페일오버
- 기존 OTel / Prometheus 스택 무변경 통합

---

## 4. 수치 표현 규칙 (§5.4)

| 규칙 | 예시 |
|------|------|
| **단위·기간·조건·출처** 필수 | "응답 지연 40% 감소 (하루 1000req, A사 실측, 2024-Q3)" |
| **환산·맥락 부여** | "빌드 10분 → 5분, 주간 2.5시간 절약 (하루 6회 배포 기준)" |
| **앵커 제공** | "업계 평균의 1/3" |
| **유리·불리 값 병기** | "지연 20% 낮고, 쓰기 처리량 15% 낮다" (Pratfall Effect — 신뢰 상승) |

## 5. 슬라이드 유형별 콘텐츠 규칙 (§5.5)

| 유형 | 규칙 |
|------|------|
| **훅/오프닝** | 청중 관련 구체 장면 또는 충격 통계 1개. **자기소개 금지** (훅 이후 1장) |
| **문제 정의** | 청중 언어로. "업계 일반 문제"가 아닌 "청중의 그 상황" |
| **해법 개요** | 한 문장 포지셔닝 + 3~5개 요소 다이어그램 |
| **작동 원리** | 단순화 다이어그램 (박스 ≤5). 정밀 버전은 부록 슬라이드 |
| **데이터/벤치마크** | 차트 1개 + 결론형 제목 + 측정 조건 각주 + 출처 |
| **고객 사례** | 청중과 동일 업종·유사 규모 우선. 정량 결과 최소 1개 |
| **경쟁 비교** | 사실 기반. 비교 기준 명시. 경쟁사 존중 톤 |
| **CTA/다음 단계** | 구체 행동 1개 + 기한 + 연락 방법 |

## 6. 목표 동사 치환표 (§3.2)

| 금지 (수단 동사) | 허용 (행동 동사) |
|----------------|----------------|
| 설명한다, 소개한다, 공유한다, 알린다 | 결정한다, 채택한다, 적용한다 |
| — | 등록한다, 승인한다, 연락한다, 파일럿한다 |

목표 문장은 `"발표 후 [청중]이 [행동]하도록 한다"` 형식으로 한 문장으로 작성.

---

## 7. AI 실패 모드 카탈로그 요약 (§9)

생성 중 아래 패턴이 발견되면 **해당 슬라이드를 폐기하고 재작성**한다.

| 코드 | 증상 | 교정 |
|------|------|------|
| §9.1 과잉 완전성 | 모든 슬라이드에 5~7개 불릿, 완전 문장 | 불릿 4개 제한, 완전 문장은 노트로 이동 |
| §9.2 제네릭 서사 | "혁신적인 솔루션을 통해…" | `forbidden-phrases.md` 대조 후 문장 폐기·재작성 |
| §9.3 환각 디테일 | 출처 없는 수치, 실존하지 않는 고객사 | `[INSERT: ...]` 플레이스홀더로 대체 |
| §9.4 Agenda-Thank you 반사 | 1번 "목차", 마지막 "감사합니다" | 훅 / CTA로 대체 |
| §9.5 평탄 계층 | 모든 텍스트 같은 크기 | 슬라이드당 시각 주인공 1개 명시 |
| §9.7 청중 불특정 | 경영진·엔지니어·PM에게 같은 톤 | §1.1 필수 입력 확인 후 청중별 분화 |
| §9.8 이모지 과다 | 제목·불릿에 이모지 장식 | 기능적 아이콘(역할 구분)만 허용 |
| §9.9 슬라이드-노트 동일화 | aside가 슬라이드 본문 반복 | 노트는 서사·수치·타이밍, 슬라이드는 키워드 |
| §9.10 목적 동사 회피 | "제품을 소개한다" 류 목표 | 행동 동사로 강제 치환 (§6 목표 동사 표) |
| §9.12 과잉 격식 | 노트가 문어체로 딱딱함 | 입말 강제 (소리 내어 읽을 수 있는지 자문) |

## 근거 스탬프와 장 전환 (v3.1)

### 근거 스탬프 `.src`

수치·인용·외부 사실이 있는 슬라이드는 **자기 출처를 화면에 단다**. 이 규칙 없이 "환각 금지 / 수치엔 출처"만 말하면 출처를 놓을 자리가 없다.

```html
<div class="src"><code>retro.md</code> · 실측 200건</div>
<div class="src unverified">추정 — 실측 전</div>
```

- 출처가 있으면 `.src`, 없으면 `.src unverified`로 **미확인임을 화면에 밝힌다**. 출처 없는 수치를 그냥 두지 않는다.
- 파일명·문서명·측정 조건처럼 **되짚을 수 있는 것**을 적는다. "내부 자료"는 출처가 아니다.
- `<code>`로 감싼 부분은 앰버로 렌더돼 파일·식별자가 눈에 띈다.
- `.slide__inner`의 직계 자식으로 두면 슬라이드 바닥에 붙는다.

### 장 전환 `.bridge`

구간이 바뀌는 슬라이드는 마지막 한 줄로 **지금 장의 결론을 다음 장의 질문으로** 바꾼다.

```html
<p class="bridge rv" style="--d:.44s">여기까지가 <strong>무엇</strong>입니다. 그럼 <strong>얼마나 걸렸을까요.</strong></p>
```

- 본문이 다 뜬 뒤 마지막에 등장시킨다(그 슬라이드에서 가장 큰 `--d`).
- 노트의 `<h4>전환</h4>`과 다른 물건이다 — 그건 발표자가 말로 하는 것이고, `.bridge`는 화면에 남는 것이다. 같은 문장을 두 곳에 쓰지 않는다.
- 모든 슬라이드에 달지 않는다. 장과 장 사이, 흐름이 꺾이는 자리에만 쓴다.
