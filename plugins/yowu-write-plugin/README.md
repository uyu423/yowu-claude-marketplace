# yowu-write-plugin

글쓰기 스킬 모음. AI Agent가 쓰는 문장은 장황해서 사람이 읽기 어렵다. 이 플러그인은 그 문제를 해결한다.

세 스킬 모두 같은 원칙을 공유한다: **기술 용어·도메인 언어·전문 용어는 그대로 두고, 그 주변 문장만 풀어 쓴다.** 낮추는 것은 문장의 부하이지 내용의 수준이 아니다.

## 스킬

| 스킬 | 대상 | 핵심 |
|------|------|------|
| `yowu-write-tech` | 설계 문서, 기술 설명, PR 설명, 장애 보고서, 기술 답변 | 정확 > 명료 > 간결 > 스타일. 두괄식, 숫자로 말하기, 명사문→동사문 |
| `yowu-write-wiki` | 위키·컨플루언스·사내 문서 | 맥락 없는 미래의 독자. 자기완결성, 시점 독립성, 검색성, 스캔 가능성 |
| `yowu-write-essay` | 에세이, 블로그, 포스트, 회고 | 구체성과 목소리. 렌즈, 리듬, 그런데/그래서 전개, 끝 문장 먼저 |

각 스킬은 두 모드로 동작한다:

- **Writing mode** — 새 글을 쓸 때. 초안을 먼저 쓰고 규칙 패스를 돈다.
- **Audit mode** — 기존 글을 감사할 때. 문제 지점을 원문 그대로 인용해 표시하고 수정안을 제시한다.

## 공통으로 잡는 AI 문체

- 부정 병렬 — "단순히 X가 아니라 Y입니다"
- 의미 인플레이션 — "혁신적인", "핵심적인", "강력한"
- 명사화·이중피동·번역투 — "검증의 수행이 요구되어집니다"
- 헤지 — "~일 수도 있을 것으로 보입니다"
- 모호성 — "성능이 크게 개선됨" (숫자 없이)
- 형식 tell — 불릿 벽, 모든 목록 3개, 과도한 볼드, 장식 이모지

## 사용 예

```
이 장애 보고서 초안 읽기 쉽게 풀어줘          → yowu-write-tech
이 내용 위키에 올릴 문서로 정리해줘           → yowu-write-wiki
이번 프로젝트 회고를 블로그 글로 써줘         → yowu-write-essay
```

## 적용 샘플 (as-is → to-be)

컨텍스트가 격리된 fresh 에이전트 2개로 만든 실제 적용 결과다. 첫 에이전트가 스타일 지시 없이 초안을 쓰고(as-is = AI 기본 문체), 둘째 에이전트가 스킬 문서만 읽고 개선했다(to-be).

### yowu-write-tech — PR 설명

| 구분 | 문장 |
|------|------|
| as-is | Redis 캐시를 도입하여 상품 조회 API의 응답 속도를 개선했습니다. 기존에는 모든 상품 조회 요청이 데이터베이스를 직접 조회하여 트래픽이 몰릴 때 응답 지연과 DB 부하가 발생했습니다. 이를 해결하기 위해 조회 빈도가 높은 상품 정보를 Redis에 캐싱하고, 캐시 미스 시에만 DB를 조회한 뒤 결과를 캐시에 적재하는 look-aside 방식을 적용했습니다. 또한 상품 정보가 변경되면 관련 캐시를 무효화하여 데이터 정합성을 유지하도록 했으며, TTL을 설정해 오래된 데이터가 남지 않도록 했습니다. 그 결과 캐시 히트 상황에서 평균 응답 시간이 크게 단축되고 데이터베이스 부하도 눈에 띄게 감소했습니다. 캐시 서버 장애 시에도 기존 DB 조회로 자연스럽게 폴백되도록 처리하여 안정성을 확보했습니다. |
| to-be | 상품 조회 API에 Redis 캐시를 도입했습니다. 기존에는 모든 조회 요청이 DB를 직접 조회했고, 트래픽이 몰리면 응답이 지연되고 DB 부하가 올라갔습니다. 이 문제를 해결하려고 조회가 잦은 상품 정보를 Redis에 캐싱했습니다. 캐시 미스일 때만 DB를 조회하고 그 결과를 캐시에 적재하는 look-aside 방식입니다. 상품 정보가 바뀌면 관련 캐시를 무효화해 데이터 정합성을 지키고, TTL을 두어 오래된 데이터가 남지 않게 했습니다. 캐시가 히트하면 응답 시간과 DB 부하가 줄어듭니다. 다만 감소 폭은 아직 측정하지 않았습니다. 캐시 서버에 장애가 나면 기존 DB 조회로 폴백합니다. |

주요 변화: "~하여 ~하도록 했습니다" 명사문·장문을 동사문으로 쪼갬. look-aside, TTL 등 용어와 원문의 합니다체는 그대로 유지. "크게 단축·눈에 띄게 감소"라는 근거 없는 수식을 지어낸 수치 대신 "아직 측정하지 않았습니다"로 정직하게 처리.

### yowu-write-wiki — 장애 대응 가이드 도입부

| 구분 | 문장 |
|------|------|
| as-is | 본 문서는 결제 서비스에서 장애가 발생했을 때 담당자가 신속하고 일관되게 대응할 수 있도록 표준 절차와 판단 기준을 정리한 가이드입니다. 결제는 매출과 직결되고 고객 신뢰에 즉각적인 영향을 미치는 핵심 서비스인 만큼, 장애 발생 시 초기 대응의 속도와 정확성이 피해 규모를 좌우합니다. 이 가이드는 장애 감지와 심각도 분류, 초동 조치, 유관 부서 및 결제 대행사(PG) 공조, 상황 전파와 복구, 사후 회고에 이르는 전 과정을 단계별로 다룹니다. 특히 야간이나 담당자 부재 상황에서도 누구나 참고해 대응할 수 있도록 연락 체계와 확인 항목을 구체적으로 명시했습니다. 실제 장애 상황에서는 본 가이드를 기준으로 하되, 현장 판단이 필요한 부분은 담당 리더와 신속히 협의하여 조치하시기 바랍니다. |
| to-be | 이 문서는 결제 서비스에 장애가 발생했을 때 담당자가 따라야 할 표준 대응 절차와 심각도 판단 기준을 정리한다. 장애를 처음 인지한 사람이 야간·주말이나 담당자 부재 상황에서도 이 문서만 보고 초동 대응을 시작할 수 있도록, 연락 체계와 단계별 확인 항목을 함께 담았다. 결제 장애는 매출과 직결되고 고객 신뢰에 즉시 영향을 주므로, 초기 대응의 속도와 정확성이 피해 규모를 좌우한다.<br><br>다루는 범위:<br>• 장애 감지와 심각도 분류<br>• 초동 조치<br>• 유관 부서 및 결제 대행사(PG) 공조<br>• 상황 전파와 복구<br>• 사후 회고<br><br>실제 장애에서는 이 문서를 기준으로 대응하되, 현장 판단이 필요한 부분은 담당 리더와 즉시 협의해 조치한다. |

주요 변화: "본 문서는 ~ 가이드입니다" 죽은 서두와 존대체를 위키 관례(한다체)로 정리. 누가 언제 읽는 문서인지(장애를 처음 인지한 사람, 야간·주말)를 첫 문단에 한 번만 명시해 자기완결성 확보 — 같은 조건을 본문에서 반복하지 않음. 다루는 범위는 열거이므로 불릿으로 분리해 스캔 가능하게. PG 같은 도메인 용어 유지.

### yowu-write-essay — 블로그 도입부

| 구분 | 문장 |
|------|------|
| as-is | 금요일 오후 4시, 배포 버튼을 누른 지 10분 만에 알림 채널이 빨간색으로 물들기 시작했다. 트래픽의 절반이 500 에러를 뱉어내고 있었고, 내가 작성한 코드가 그 원인이라는 사실을 깨닫는 데는 오래 걸리지 않았다. 입사 후 처음 겪는 대규모 장애 앞에서 머릿속은 하얘졌고, 손은 떨렸으며, 롤백 절차조차 제대로 기억나지 않았다. 그날 밤 장애를 수습하며 배운 것들은 그 어떤 교육이나 문서에서도 얻지 못했던 값진 교훈이었다. 이 글에서는 그 몇 시간의 기록과 함께, 장애가 나에게 가르쳐준 시스템과 사람에 대한 이야기를 풀어보려 한다. |
| to-be | 금요일 오후 4시, 배포 버튼을 눌렀다. 10분 뒤, 알림 채널이 빨갛게 물들기 시작했다. 트래픽의 절반이 500 에러를 뱉어내고 있었고, 그 원인이 내가 짠 코드라는 걸 깨닫는 데는 오래 걸리지 않았다. 입사 후 처음 겪는 대규모 장애였다. 머릿속은 하얘졌고, 손은 떨렸고, 그토록 여러 번 들었던 롤백 절차조차 하나도 기억나지 않았다. |

주요 변화: 문장 길이 변주로 리듬 생성(짧게 → 중간 → 길게). "값진 교훈이었다" 상투구와 "이 글에서는 ~을 풀어보려 한다"는 자기지시적 예고 문장을 삭제 — 글이 무엇인지 선언하는 대신 다음 문단이 보여주게 둠. 초안에 없는 필자의 내면·태도를 지어내지 않음(재료 규칙).
