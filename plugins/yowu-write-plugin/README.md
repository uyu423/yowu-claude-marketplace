# yowu-write-plugin

글쓰기 스킬 모음. AI Agent가 쓰는 문장은 장황해서 사람이 읽기 어렵다. 이 플러그인은 그 문제를 해결한다.

다섯 스킬이 [한국어 문장 공통 규범](references/korean-sentence.md)을 공유하고(`yowu-write-comment`는 부분 적용), 그 위에 같은 원칙을 얹는다: **기술 용어·도메인 언어·전문 용어는 그대로 두고, 읽는 부하만 낮춘다.** 낮추는 것은 문장의 부하이지 내용의 수준이 아니다. (주석은 푸는 대신 지우는 쪽이 정답일 때가 많다.)

## 스킬

| 스킬 | 대상 | 핵심 |
|------|------|------|
| `yowu-write-tech` | 설계 문서, 기술 설명, PR 설명, 장애 보고서, 기술 답변 | 정확 > 명료 > 간결 > 스타일. 두괄식, 숫자로 말하기, 명사문→동사문, 산문형·단언형·혼합형 판단, 열거·매핑·구조를 목록·표·코드 블록으로 승격 |
| `yowu-write-wiki` | 위키·컨플루언스·사내 문서 | 맥락 없는 미래의 독자. 자기완결성, 시점 독립성, 검색성, 스캔 가능성, 산문형·단언형·혼합형 판단, 열거·매핑·구조를 목록·표·코드 블록으로 승격 |
| `yowu-write-essay` | 에세이, 블로그, 포스트, 회고 | 구체성과 목소리. 렌즈, 리듬, 그런데/그래서 전개, 끝 문장 먼저 |
| `yowu-write-meeting` | 회의록 문장 | 회의에 없던 팀원이 각 줄을 한 번에 이해. 상태 명시(합의/미정/후속), 개조식 압축, 없는 내용 지어내지 않기. 구조·양식은 팀 포맷의 몫 |
| `yowu-write-comment` | 한국어 코드 주석 | WHAT 금지·WHY 중심. AI 문체·번역투 금지, 기술 용어 영문 원형 유지, 자명한 코드엔 주석 0개 |

각 스킬은 두 모드로 동작한다:

- **Writing mode** — 새 글을 쓸 때. 초안을 먼저 쓰고 규칙 패스를 돈다.
- **Audit mode** — 기존 글을 감사할 때. 문제 지점을 원문 그대로 인용해 표시하고 수정안을 제시한다. tech·wiki·essay·meeting은 감사 결과에 칭찬을 붙이지 않는다.
  - **비평만** — 사용자가 직접 고치겠다고 하면 수정안 없이 무엇이 문제이고 무엇을 확인할지만 짚는다(tech·wiki·essay). essay는 사용자가 자기 글이라고 밝히면 이것이 기본이다. "다듬어줘"만으로는 수정안을 쓰지 않는다. 모델이 고른 낱말이 필자의 목소리를 밀어내지 않게 한다.

## 공통으로 잡는 AI 문체

- 부정 병렬 — "단순히 X가 아니라 Y입니다", "A인가, B인가", "더 이상 A가 아니라 B". 구체적인 대비라도 두 번 이상이면 하나만 남김. 대비를 남길 때도 X는 독자가 실제로 떠올릴 법한 생각이어야 함
- 결산·강조 공식 — "핵심은 ~다", "결국 ~로 이어진다", "~하는 이유다", "~다는 것이다", "결론적으로", "~라는 분석이다"(출처 없이), "과제도 남아 있다"
- 연결어미 뒤 쉼표 — "도입했지만, 그대로였다"
- 생성형 은유 — "진단은 서늘하다", "잠식하다·청사진·신호탄", 같은 은유의 반복
- 의미 인플레이션 — "혁신적인", "핵심적인", "강력한", 형용사 셋을 나란히 붙인 "빠르고 안정적이며 확장 가능한" (tech·wiki·essay)
- 명사화·이중피동·번역투 — "검증의 수행이 요구되어집니다", "운영 환경에서의 검증", 세 겹 이상 쌓인 관형절
- 범용 동사·추상 주어 — "체계를 강화했다"(무엇을 했는지 없이), "응답 속도 개선에 기여했다", "이번 장애는 ~을 보여준다", "높은 히트율을 가지고 있다"
- 경동사 — "검토를 진행했다", "롤백을 수행했다", 단순히 쓴다는 뜻의 "활용한다"
- 평판 표현 — "주목받고 있다", "각광받고 있다" (누가 그랬는지 없이)
- 가운뎃점 나열 — 줄글에서 "설계·구현·운영"처럼 셋 이상을 `·`로 묶음
- 헤지 — "~일 수도 있을 것으로 보입니다"
- 모호성 — "성능이 크게 개선됨" (숫자 없이)
- 형식 tell — 불릿 벽, 모든 목록 3개, 과도한 볼드, 강조용 따옴표 남발, 장식 이모지
- 챗봇 잔재 — "물론입니다!", "도움이 되셨길 바랍니다" (tech·wiki), 흉내 낸 공감·맞장구 "얼마나 답답하셨을지 이해합니다", "전적으로 맞는 말씀입니다" (tech)
- 대화 잔재 — "요청하신 대로", 작업 중에 버린 초안을 기각하는 "X 대신 Y" (tech·wiki·comment), 작업 중에만 있던 중간 상태 (tech·comment)
- 분량 부풀리기 — 한두 문장짜리 변경에 붙인 배경·기대 효과·향후 계획 단락 (tech), 재료에 없는 의의·교훈 (essay)
- 리듬 단조 — 80자 이상 문장 부재, 현재형 `~한다` 4문장+ 연속, 당위로 끝나는 문단 2개+ (essay, 당위 결말은 wiki도)
- 열거·매핑 매몰 — 식별자 여러 개를 `·`로 이어 한 문장에, ①②③ 열거를 한 문장에, shape을 인라인 백틱에 (tech·wiki, meeting은 부분)

잡지 않는 것도 정했다. `~것이다` 종결은 사람 글에서 더 흔한 정상 종결이라 잡지 않는다. `~를 통해`와 문두 접속사는 한 문단에 세 번 이상 나올 때만 잡는다. 부정 대구 변종은 한 문서에 두 번 이상일 때만 잡는다. 고치는 과정에서 원문에 없던 결산 표현·쉼표·대구를 새로 만드는 것은 tech·wiki·essay·meeting에서 실패로 친다. comment는 상투구·결산 표현의 주입만 막는다. 고치면서 계획을 완료로, 당위를 사실로 바꾸거나 격식을 올리는 것도 실패다. 나란히 놓인 두 사실을 `그래서`로 이어 없던 인과를 만드는 것도 같다(공통 10번). 결과물에 입력에 없던 숫자·약속·조건이 생기는 것도 실패다. 내기 전에 대조해서 지우거나 `[확인 필요]`로 남긴다(공통 12번). essay에서는 "솔직히 말하면", "당시", "힘들다" 같은 사람 글의 흔적을 지우지 않는다.

## 한국어 문장 공통 규범

매체별 스킬 밑에 공통 하부 규범이 하나 깔려 있다: [`references/korean-sentence.md`](references/korean-sentence.md). 한국어를 쓸 때 매체와 무관하게 반복되는 실패를 모았다. 각 스킬이 풀어쓰기에 들어가기 전에 이 파일을 읽고 함께 적용한다.

| 조항 | 내용 |
|------|------|
| 1 | 명확하게 쓰라는 규범이지, 외국어를 번역하라는 지시가 아니다 |
| 2 | 명사구를 `~의`로 사슬처럼 잇지 말고 서술어로 푼다. `~적 N` 체인, 이중 조사(`~에서의`), 세 겹 이상 쌓인 관형절도 같은 증상 |
| 3 | 명사구·부사구·연결어미로 문장을 끊지 않고 서술어로 끝맺는다 |
| 4 | 필수적인 경우가 아니면 조사와 어미를 생략하지 않는다 |
| 5 | 엠대시(`—`)를 자제하고 접속사로 앞뒤 관계를 밝힌다. 관계를 특정할 수 없으면 문장을 끊는다. 줄글에서 셋 이상을 가운뎃점(`·`)으로 묶지 않는다 |
| 6 | 사용자가 채팅에서 쓴 어조를 산출물의 어체로 삼지 않는다 |
| 7 | 조사를 틀리게 쓰지 않는다. 백틱 식별자 뒤 조사는 한국어 발음의 받침으로 고른다 |
| 8 | 연결어미(`-고`·`-며`·`-지만`·`-면서`·`-아서`·`-어서`) 뒤에 쉼표를 찍지 않는다. 감사는 문서 3회+일 때, 고친 결과에서 늘면 실패 |
| 9 | 결산·강조 공식(분열문, `결국`, `~하는 이유다`, `~다는 것이다`, `~할 때다`, 결말 `향후`·`앞으로`·`중장기적으로`, 결산 라벨, 무주체 판정, 평판 표현, 빈 반론 문패)으로 문단·글을 닫지 않는다 |
| 10 | 고치면서 서법·시제·격식·논리 관계를 바꾸지 않는다. 계획·당위·조건을 사실로 만들지 않는다. `했다`를 `하였다`로 올리지 않는다. 원문에 없던 인과·대조 접속을 넣지 않고 있던 것은 지우지 않는다 |
| 11 | 행위를 범용 동사(`강화`·`개선`·`확대`·`확보`·`마련`·`구축`·추상 목적어의 `설계`)나 추상 주어 + 만능 동사로 뭉뚱그리지 않는다. `~에 기여한다`, 경동사(`N을 진행/수행/실시하다`)도 같다. 구체 행위는 원문에 있는 것만 |
| 12 | 끝내기 전에 결과물의 숫자·날짜·이름·약속·조건을 뽑아 입력과 대조한다. 없으면 지우거나 `[확인 필요]` 빈칸으로 남긴다 |

**매체 규칙이 공통 규범을 이긴다.** 스킬마다 조정이 다르므로 각 SKILL.md의 "한국어 문장 공통 규범" 절에 그 내용을 적어 두었다.

| 스킬 | 매체별 조정 |
|------|------|
| `yowu-write-tech` | 완성형 종결은 어체 변경이 아니므로 원문의 합니다체/한다체는 보존한다. 단언형·혼합형으로 판단된 섹션의 불릿은 `yowu-write-meeting`과 같은 개조식(`~함`/`~됨`/`~임`) 종결을 따른다. 목록·표·코드 블록을 이끄는 도입 문장의 콜론은 5번의 대상이 아니다. 11번 문턱(한 문단 3회+)에 못 미치는 범용 동사는 모호성 압축 규칙이 잡는다 |
| `yowu-write-wiki` | 섹션 제목, 열거용 불릿, 그리고 단언형·혼합형으로 판단된 결론부 불릿(개조식 `~함`/`~됨`/`~임`)이 완성형 종결에서 제외된다. **절차 목록의 각 단계는 여전히 제외가 아니다.** 목록·표·코드 블록을 이끄는 도입 문장의 콜론은 5번의 대상이 아니다. 평서형(한다체) 통일은 10번의 격식 보존보다 우선한다 |
| `yowu-write-essay` | 리듬을 위한 의도적 단문·명사구는 완성형 종결과 조사 생략의 예외. 8번(연결어미 쉼표)은 리듬 장치가 아니므로 예외 없이 적용. 목소리 절의 연설조 교정은 10번의 격식 보존보다 우선하되 종결 어체는 보존 |
| `yowu-write-meeting` | 12번은 쓰거나 고치면서 새로 생긴 내용만 본다. 녹취 대조는 범위 밖이다. 불릿의 개조식 `~함`은 완성형 종결의 대상이 아니다. 3번은 줄글 문단에만 적용. 9번의 결말 시간어(`향후`·`앞으로`·`중장기적으로`)는 결정·액션 아이템에서 계획을 표시하므로 둔다. `향후 인지 사항` 같은 상태 라벨도 대상이 아니다. 개조식 종결 통일은 10번의 격식 보존보다 우선한다. 다만 `~하기로 함`을 `~함`으로 줄여 계획을 완료로 만들면 안 된다 |
| `yowu-write-comment` | **부분 적용.** 2번(명사구 사슬), 6번(어조 비모방), 7번(조사 오용)만 가져온다. 8~12번은 적용하지 않는다. 12번의 역할은 사실 패스가 맡는다 |

조항 4는 방향을 오해하기 쉽다. **과압축된 문장을 되살리는 규칙이지, 완성된 문장을 늘리는 규칙이 아니다.** 조항 4와 각 스킬의 필러 삭제 규칙이 같은 축의 양 끝이다. 부사와 양태 보조 용언은 이 조항의 수단이 아니다. 상세는 규범 문서의 "되살릴 것과 되살리지 말 것" 절에 있다.

## 상시 적용 (SessionStart 훅)

스킬은 글쓰기 작업으로 판단될 때만 불린다. 평소 채팅 답변이나 PR 설명처럼 스킬 없이 쓰는 한국어에는 규칙이 닿지 않는다. 그래서 플러그인이 `SessionStart` 훅으로 [`references/always-on.md`](references/always-on.md) 카드를 세션 컨텍스트에 넣는다. 세션을 새로 열 때, 재개할 때, `/clear`와 컨텍스트 압축 뒤에 다시 넣는다.

- 카드는 쓰는 도중에 피할 수 있는 표면 패턴과 내기 전 대조만 담는다. 공통 규범을 대신하지 않는다. 스킬이 불리면 스킬은 여전히 공통 규범 전문을 읽는다.
- 한국어로 쓸 때만 적용하라고 카드에 적었다. 그래도 매 세션 약 2.9KB가 컨텍스트에 들어간다.
- 끄려면 환경 변수 `YOWU_WRITE_ALWAYS_ON=0`을 설정한다. 스킬은 그대로 쓸 수 있다.

## 사용 예

```
이 장애 보고서 초안 읽기 쉽게 풀어줘          → yowu-write-tech
이 내용 위키에 올릴 문서로 정리해줘           → yowu-write-wiki
이번 프로젝트 회고를 블로그 글로 써줘         → yowu-write-essay
이 회의록 팀원들이 읽기 쉽게 다듬어줘         → yowu-write-meeting
이 코드에 한국어 주석 달아줘                  → yowu-write-comment
```

## 적용 샘플 (as-is → to-be)

컨텍스트가 격리된 fresh 에이전트 2개로 만든 실제 적용 결과다. 첫 에이전트가 스타일 지시 없이 초안을 쓰고(as-is = AI 기본 문체), 둘째 에이전트가 스킬 문서만 읽고 개선했다(to-be).

### yowu-write-tech — PR 설명

| 구분 | 문장 |
|------|------|

### yowu-write-meeting — 회의록 논의 사항

회의록은 여러 줄짜리 산출물이라, 한 문장 표 대신 원문 전체의 before/after를 그대로 싣는다. 이 스킬은 문서 구조는 그대로 두고 문장만 손본다는 점에 주목.

**as-is** (스타일 지시 없이 쓴 AI 기본 문체):

```
## 논의 사항

### 1. 상품 조회 API 응답 속도 개선
- 상품 조회 API의 응답 속도가 느리다는 이슈가 제기되었다.
- 개선 방안으로 Redis 캐시 도입이 제안되었으나, 도입에 따른 비용이 명확하지 않아 추가 검토가 필요하다는 데 의견이 모였다.
- **Action Item**: 김개발 님이 다음 주까지 Redis 캐시 도입 비용을 산정하기로 함.

### 2. 알림 발송 지연 문제
- 알림 발송이 간헐적으로 약 5분가량 지연되는 문제가 보고되었다.
- 현재 정확한 원인은 파악되지 않은 상태이다.
- **Action Item**: 이영희 님이 관련 로그를 분석하여 원인을 파악하는 중.

### 3. 신규 정산 배치 실행 시각
- 신규 정산 배치를 매일 새벽 3시에 실행하기로 합의하였다.

### 4. 결제 모듈 리팩토링
- 결제 모듈 리팩토링 필요성이 언급되었으나, 이번 분기 내 진행은 현실적으로 어렵다는 의견이 우세하였다.
- 이에 따라 해당 작업은 다음 분기로 연기하기로 하였다.
```

**to-be** (yowu-write-meeting 적용):

```
## 논의 사항

### 1. 상품 조회 API 응답 속도 개선
- 상품 조회 API 응답 속도가 느림.
- 개선안으로 Redis 캐시 도입이 제안됨. 미정 — 도입 비용이 명확하지 않아 추가 검토 필요.
- **Action Item**: 김개발 님이 다음 주까지 Redis 캐시 도입 비용을 산정하기로 함.

### 2. 알림 발송 지연 문제
- 알림 발송이 간헐적으로 약 5분가량 지연됨. 원인 미파악.
- **Action Item**: 이영희 님이 관련 로그를 분석해 원인을 파악 중.

### 3. 신규 정산 배치 실행 시각
- 신규 정산 배치를 매일 새벽 3시에 실행하기로 합의함.

### 4. 결제 모듈 리팩토링
- 결제 모듈 리팩토링 필요성이 나왔으나, 이번 분기 내 진행은 어렵다는 의견이 우세함.
- 합의 — 다음 분기로 연기.
```

주요 변화: **문서 구조(섹션 구성·순서·`**Action Item**` 라벨·불릿 양식)는 그대로 두고 문장만 손봤다** — 이 스킬은 구조를 재편하지 않는다. 얼버무린 상태를 재료가 말한 그 결과로 못 박음("추가 검토가 필요하다는 데 의견이 모였다" → `미정 — ...`, "연기하기로 하였다" → `합의 — 다음 분기로 연기`, 재료에 없는 합의는 만들지 않음). `~되었다/~하였다` 서사체를 개조식(`~함/~됨`)으로 통일하고 피동·"이에 따라" 같은 장황 접속을 걷어냄. `Redis`·`상품 조회 API` 등 용어와 사람 이름·수치·기한(5분·새벽 3시·다음 주)은 보존. 발화자 귀속·수치·합의 수준의 사실 검증은 이 스킬의 몫이 아니다(원문 대조는 별도 기능).

가져오지 않은 것과 그 이유:

- **장문 결핍·불릿 산문화를 tech·wiki에 적용하는 것.** 두 매체는 한 문장 한 생각과 단언형 불릿이 매체 규칙이다. 대신 wiki 과교정 방지에 "한 호흡에 읽히는 긴 문장은 쪼개지 않는다"만 넣었다(tech에는 이미 있음).
- **종결 단조를 tech·wiki에 적용하는 것.** 종결을 바꾸려면 문장 구조를 바꿔야 해서 시제·서법이 흔들린다. 한다체 기술 문서에서 `~한다`가 이어지는 것은 정상이다. tech의 "어체를 건드리지 않는다"와도 부딪힌다.
- **당위 결말 반복을 meeting에 적용하는 것.** 액션 아이템은 원래 당위로 끝난다.
- **단정 전환 전면 금지(G-1).** tech·wiki의 "판단을 내리거나 미확인으로" 처방을 유지했다. 헤지가 의미인 텍스트만 예외로 뒀다.
- **실행 장치.** 변경률 게이트, Python 스크립트, 서브에이전트 파이프라인, 등급 채점은 가져오지 않았다.
- **85개 패턴 전체.** SKILL.md는 매번 로드되므로 판별력이 실측된 것과 매체 규칙에 맞는 것만 가져왔다.
- **피동 진행 "~되고 있다" 밀집(A-20).** 실측은 확증이다. 하지만 처방("심화되고 있다" → "심해졌다")이 시제를 바꿔 공통 10번과 부딪힌다.
- **"~할 수 있다" 반복 분산(A-10), 이중 완곡 접기(G-2).** tech·wiki의 헤지 규칙과 처방이 겹친다. 헤지가 의미인 텍스트의 예외만 가져왔다.
- **"~에 대해" 밀집(A-1).** 사람이 3배 더 쓰는 표현이다.
- **"1) 2) 3)" 인덱싱(C-9), 열거 도입 "다음과 같다"(D-3).** tech·wiki는 열거를 목록으로 꺼내고 도입 문장을 허용한다. 처방 방향이 반대다.
- **무시간 도입·등장인물 부재·인용 결핍(DS-1·DS-3, 인용 결핍).** 처방하려면 없는 사실을 지어내야 한다.
- **"즉" 남발(H-4), "먼저·반면·결국" 3단(C-7), 콜론 부제 헤딩(C-10).** 실측이 없고 기존 규칙(필러 삭제, 소제목 남발)이 대부분 덮는다.
- **워터마크 제거.** 제거됐는지 측정할 탐지기가 없다. 투명성 장치를 우회하는 기능이 된다.

챗봇 잔재("물론입니다!", "도움이 되셨길 바랍니다")는 im-not-ai에 해당 패턴이 없다. 실측 근거 없이 필러 삭제 원칙으로 넣었다.

### LLM Voice 논의에서 가져온 것 (2026-10)

Martin Fowler의 [LLM Voice](https://martinfowler.com/bliki/LLM-Voice.html)와 [GeekNews 토론](https://news.hada.io/topic?id=36244), 거기 연결된 글과 [Hacker News 토론](https://news.ycombinator.com/item?id=50290177)을 근거로 삼았다. 실측은 없다. 원칙과 관찰 사례에서 온 규칙이다. 감사하는 태도, 고칠 때의 주입 금지, 기존 규칙의 예외 조건을 손봤다. 블록리스트에는 대화 잔재와 흉내 낸 공감을 더했고 분량 규칙을 넣었다.

기존 규칙을 뒷받침하는 외부 연구도 있다. Clark·Martin·Mahowald(2026, [arXiv 2610.29162](https://arxiv.org/abs/2610.29162))는 영어 글에서 9개 모델 모두가 사람보다 무생물 주어에 생물 동사를 더 붙인다고 보고했다. 대부분의 모델은 명사를 더 쌓았고 의존 거리도 더 길었다. 공통 11번(추상 주어 + 사람의 동작)과 2번(명사 사슬, 세 겹 이상 관형절)이 잡는 증상이다. 영어 대상 연구라 배수는 옮기지 않았다.

가져오지 않은 것:

- **맥락 없는 모델에게 원문과 수정본을 비교시키기(Ptacek).** 수정한 사실을 아는 모델은 수정본 편을 든다는 지적은 맞다. 하지만 서브에이전트 파이프라인이라 위 "실행 장치"와 함께 넣지 않았다.
- **부사 목록(매우·정말·실제로·안타깝게도).** 영어 관찰이고 한국어 실측이 없다. 공통 4번이 뜻 있는 부사를 보호한다.
- **한 문장짜리 문단의 연속.** 관찰은 있지만 실측이 없다.
- **AI 탐지기 기준에 맞추기.** Fowler가 지적하듯 탐지 결과는 이미 생긴 독자의 거부감을 되돌리지 못한다. 패턴 자체를 목표로 삼으면 언어가 나빠진다는 지적도 있다(위 cyberneticforests 글). 이 플러그인은 읽는 부담을 줄이려고 만들었다.

### AI Trend Library 가이드에서 가져온 것 (2026-11)

[AI 티 나는 한국어 줄이기](https://aitrend-library.pages.dev/g/ai-tells-korean) 가이드를 근거로 삼았다. 이 가이드는 10개 패턴, 설정에 넣을 지침, 보내기 전 점검 프롬프트를 제시하고 작은 실험 결과를 붙였다. 실험은 메일 2편을 Claude Sonnet으로 각 3회씩, 지침 유무로 나눠 모두 12회 생성한 것이다.

측정은 이렇게 읽었다. 지침을 넣자 `진행`은 11건에서 1건으로 줄었다. 하지만 줄어든 낱말은 그것 하나였다. 입력에 없는 약속·조건이 들어간 메일은 지침을 넣어도 6편 중 5편에서 3편으로 줄었을 뿐이다. 숫자 유지와 유보 표현 유지는 지침 유무와 상관없이 6/6이었다. 표본이 12회라 배수로 일반화하지 않는다. 다만 두 방향의 결론은 받아들였다. 상시 지침은 생성 단계에서 특정 낱말을 줄이는 데 효과가 있다. 주입은 지침으로 잘 막히지 않는다. 그래서 상시 카드를 넣되 기대치를 낮게 잡고, 주입은 문장 규칙이 아니라 결과물을 다시 훑는 절차(공통 12번)로 막는다.
