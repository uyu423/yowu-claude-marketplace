# yowu-write-comment: 한국어 코드 주석 쓰기

판정이 먼저다. **이 주석이 필요한가** — 코드가 이미 말하고 있으면 답은 삭제다. 남길 주석의 목표는 하나다. **읽는 사람이 보는 순간, 더 생각하지 않고 즉시 이해한다.** 주석을 읽고 다시 코드를 봐야 하거나, 문장을 두 번 읽어야 하면 실패한 주석이다.

기준은 이것이다: **옆자리 동료가 코드 보다가 구두로 툭 설명해주는 말투.** 그 이상 꾸미면 AI 티다.

## 대원칙: 짧게 쓰는 것이지, 정보를 깎는 게 아니다

낮추는 것은 읽기 부하이지 정보량이 아니다. 수식어와 군더더기를 깎되, 도메인 규칙·함정 경고·설계 의도는 문장이 길어져도 지킨다. 그리고 이 스킬의 절반은 쓰는 규칙이 아니라 지우는 규칙이다 — 좋은 주석만큼이나 "주석 없음"이 정답인 경우가 많다.

## 적용 범위

- 지금 작성·수정하는 코드의 주석에 적용한다. 요청과 무관한 기존 주석은 건드리지 않는다. 파일 전체 감사는 "주석 정리·리뷰"를 요청받았을 때만.
- 코드를 고쳤으면 그 코드에 딸린 기존 주석이 여전히 맞는지 확인한다. 틀렸으면 같은 커밋에서 고친다.
- "주석 달아줘"를 받았는데 코드가 자명하면 주석을 지어내지 않는다. WHY가 있는 지점(의도·제약·함정)에만 달고, 없으면 "달 주석이 없다"고 말한다.
- 팀이 영문 주석을 쓰는 코드베이스면 적용하지 않는다. 판단 기준은 대상 파일과 주변 파일의 기존 주석 언어.

## 스킬 분기 (형제 스킬과의 경계)

- 코드 안에 다는 주석(인라인, 블록, docstring) → **yowu-write-comment** (이 스킬)
- PR 설명, 코드 리뷰 코멘트, 기술 문장 → **yowu-write-tech**
- 위키·컨플루언스 문서 → **yowu-write-wiki** / 회의록 → **yowu-write-meeting** / 에세이·블로그 → **yowu-write-essay**
- "코멘트 정리해줘"처럼 코드 안 주석인지 리뷰 코멘트인지 불분명한 요청 → 대상을 먼저 확인한다.
- 대상이 코드 안의 주석이면, 다른 write 스킬의 어체·격식 규칙보다 이 스킬의 문체 규칙이 우선한다.

## 문체: 한국 개발자들이 실제로 쓰는 문체

- 종결은 간결한 평서형(`~한다`, `~된다`) 또는 명사형(`~함`, `~됨`, `~임`) 중 하나. 판정 순서: ① 같은 파일에 주석이 있으면 그 종결을 따른다 ② 없으면 같은 디렉터리 인접 파일을 본다 ③ 그래도 없으면 명사형을 기본값으로 한다.
- 한 파일 안에서 종결 스타일을 섞지 않는다.
- 존댓말(`~합니다`, `~해주세요`) 금지. 주석은 문서가 아니라 메모다.
- 한 주석 = 한 가지 정보. 문장은 짧게 끊고, 접속사로 잇지 않는다. 근거가 필요하면 두 문장으로 끊어 쓴다.
- 인라인(꼬리) 주석은 짧게. 한 줄에 안 들어가면 코드 위로 올린다.

## AI 문체 전면 금지 (최우선)

AI가 쓴 티가 나는 주석은 전부 실패다. 다른 규칙과 충돌하면 이 규칙이 이긴다. 금지 목록:

- **장황한 서두**: `이 함수는 ~하는 역할을 수행한다` → `~한다`로 끝. 주어 생략.
- **과잉 수식**: `효율적으로`, `안전하게`, `적절히`, `원활하게` 같은 근거 없는 부사. 숫자나 이유가 없으면 삭제.
- **번역투**: `~하는 것을 허용한다`, `~에 의해 호출된다`, `~할 수 있게 해준다`, `~라고 할 수 있다` → 능동태 직설 문장으로.
- **하나 마나 한 설명**: `초기화를 진행한다`, `값을 반환한다` 같이 코드만 봐도 아는 내용.
- **부정 병렬**: `단순한 X가 아니라 Y` → 기각 절반(X)을 지우고 Y를 직접 쓴다. Y가 구체적 메커니즘이면 예외.
- **대칭 나열, 3단 구성 강박**, "즉, 다시 말해" 류의 재진술.

판정 기준은 문서 상단의 그 한 줄 — **동료가 구두로 툭 설명해주는 말투**를 넘게 꾸몄는가.

## 용어 보존 규칙

- `deadlock`, `race condition`, `debounce`, `polling`, `fallback`, `mutex`, `idempotent` 같은 기술 용어는 영문 그대로. 억지 번역 금지 ("교착 상태 방지" ✗ → "deadlock 방지" ○).
- 단, 한국 개발자들 사이에 이미 한글로 굳은 말(캐시, 락, 큐, 트랜잭션, 커밋, 롤백, 스레드, 콜백)은 통용 표기를 따른다. 판단 기준은 "회사 슬랙에서 뭐라고 부르나".
- 영문 용어 + 한국어 조사는 자연스럽게 붙인다: `deadlock이 발생하면`, `retry를 3회까지만`.
- 클래스명, 함수명, 변수명, 상수는 주석에서도 코드 표기 그대로. 번역하거나 풀어쓰지 않는다.

## WHAT 금지, WHY 중심

코드가 이미 말하는 '무엇'을 주석으로 반복하지 않는다. `i += 1  // i를 1 증가` 같은 주석이 나오면 이 스킬이 실패한 것이다.

주석이 담을 것은 코드에 안 보이는 정보다:

- 왜 이렇게 짰는지 (의도, 설계 결정)
- 왜 뻔한 방법을 안 썼는지 (트레이드오프, 시도했다 실패한 접근)
- 도메인 규칙, 외부 제약 (API 스펙, 법적 요건, 레거시 호환)
- 함정 경고 (`이 순서 바꾸면 deadlock 남`)

'무엇'을 설명해야만 이해되는 코드라면, 주석을 달지 말고 코드를 고치라고 제안한다. 변수명 개선, 함수 추출이 먼저다. 지역 변수명처럼 그 자리에서 끝나는 변경은 바로 고쳐도 되지만, 함수·클래스 이름처럼 호출부에 파급되는 변경은 제안만 하고 확인을 받는다.

## 달지 말아야 할 주석

- 코드 내용 반복 주석
- 주석 처리된 죽은 코드 — git이 기억한다. 지운다.
- 변경 이력, 작성자, 날짜 — git blame이 한다.
- 닫는 괄호 표시 주석 (`} // end of for`)
- 사실과 어긋난 주석 — 코드를 수정하면 주석도 같은 커밋에서 고친다. **틀린 주석은 없는 주석보다 나쁘다.**

## 관용 태그와 문서화 주석

- `TODO:`, `FIXME:`, `HACK:`, `NOTE:` 태그는 영문 대문자 관행 그대로 쓰고, 뒤에 이유를 붙인다. `// TODO: 서버 v2 배포되면 이 fallback 제거` — 이유 없는 `// TODO: 나중에 수정`은 금지. 언제 무엇이 되면 지울 수 있는지를 쓴다.
- JSDoc, docstring, KDoc, Javadoc 등 문서화 주석은 해당 포맷 문법을 유지하되 설명문은 이 스킬의 한국어 규칙을 따른다. `@param`, `@returns` 태그는 그대로.
- 문서화 주석은 public API, 공용 유틸, 타입이 안 드러나는 곳에만. 전 함수 강제 금지.

## 감지 신호 (도구 없이)

- 주석의 명사를 뽑았을 때 바로 아래 코드의 식별자와 겹치면 WHAT 반복이다. (`// 캐시에서 값을 조회` vs `cache.get(key)`)
- `~하는 것을`, `~에 의해`, `~할 수 있게`가 보이면 번역투다.
- 부사가 있는데 같은 주석 안에 숫자나 이유가 없으면 과잉 수식이다.
- 주석을 지웠다고 상상했을 때 잃는 정보가 없으면 실제로 지운다.

## 좋은 주석 / 나쁜 주석

**1. WHAT 반복 → 삭제** (TypeScript)

```ts
// 나쁨: 코드가 이미 말함
// 캐시에서 값을 조회한다
const cached = cache.get(key);
```

좋음: 주석 없이 `const cached = cache.get(key);` 한 줄이면 끝.

**2. 값의 근거** (Kotlin)

```kotlin
// 나쁨: 값을 읽어줄 뿐
// 배치 크기를 500으로 설정
const val BATCH_SIZE = 500

// 좋음: 왜 500인지
// 1000부터 DB lock 대기가 급증함. 부하 테스트로 500 확정
const val BATCH_SIZE = 500
```

**3. 함정 경고** (TypeScript)

```ts
// 나쁨: 경고인데 뭐가 위험한지 없음
// 순서 중요
releaseLock();
await flush();

// 좋음: 순서를 바꾸면 무슨 일이 나는지
// 순서 주의: flush가 내부에서 같은 락을 잡음. 락 쥔 채로 부르면 deadlock
releaseLock();
await flush();
```

**4. 문서화 주석** (Kotlin)

```kotlin
// 나쁨: 존댓말 + 장황한 서두 + 코드만 봐도 아는 내용
/** 이 함수는 amountUsd와 rate를 받아 원화 금액을 반환하는 역할을 수행합니다. */
fun toKrw(amountUsd: BigDecimal, rate: BigDecimal): Long

// 좋음: KDoc 문법은 유지, 설명은 코드에 안 보이는 도메인 규칙만
/**
 * 원 단위 절사. 회계 정산 기준이라 반올림하면 대사가 안 맞음
 *
 * @param rate 결제 시점 고시 환율. 현재 환율 쓰면 안 됨
 */
fun toKrw(amountUsd: BigDecimal, rate: BigDecimal): Long
```

**5. 외부 제약** (TypeScript)

```ts
// 나쁨: 근거 없는 부사
// 타임아웃을 적절히 설정해서 안정성을 확보한다
const TIMEOUT_MS = 2500;

// 좋음: 외부 시스템의 제약
// PG사 API가 3초에 자체 취소함. 그 전에 끊어야 우리 재시도와 PG 취소가 겹치지 않음
const TIMEOUT_MS = 2500;
```

**6. 주석 대신 코드 수정** (Kotlin)

```kotlin
// 나쁨: 이름이 못 하는 일을 주석이 대신함
// d에는 유저별 마지막 로그인 시각이 들어 있음
val d = load()

// 좋음: 주석을 지우고 이름을 고침
val lastLoginByUser = load()
```

예시의 좋음 주석은 기본값인 명사형 기준이다. 코드베이스가 평서형이면 같은 내용을 평서형으로 쓴다.

## Writing mode (코드를 쓰면서 주석을 달 때)

주석은 코드와 함께 자연스럽게 초안을 쓴다. 완성 후 감사 패스를 돈다:

1. **삭제 패스**: WHAT 반복, 자명한 주석, 죽은 코드를 지운다. 주석 수가 줄어드는 게 정상이다.
2. **문체 패스**: AI 문체·번역투·과잉 수식을 걷어내고, 파일 내 종결 스타일을 통일한다.
3. **사실 패스**: 남은 주석이 코드와 일치하는지 확인한다. 숫자, 순서, 조건 전부.

## Audit mode (기존 주석을 감사할 때)

문제 주석을 **원문 그대로** 인용하고 수정안을 제시한다. 재작성은 코드에서 직접 확인한 사실만 쓴다. WHY를 모르면 지어내지 말고 '삭제' 또는 '작성자 확인 필요'로 남긴다. 문제가 없으면 `WRITE-COMMENT AUDIT: 문제 없음` 한 줄만 출력한다. 아래는 형식 예시일 뿐이니 항목을 고정하지 말고 실제 발견된 것만 나열한다:

```
WRITE-COMMENT AUDIT:
  WHAT 반복:  FLAG — "// 유저 목록을 순회한다" → 삭제 (코드가 이미 말함)
  AI 문체:    FLAG — "// 안전하게 초기화를 진행하는 역할을 수행" → "// 초기화 순서 고정. config 로드 전에 돌면 NPE"
  번역투:     FLAG — "// 이 값은 캐시에 의해 관리된다" → "// 캐시가 관리하는 값. 직접 수정 금지"
  부정 병렬:  FLAG — "// 단순한 캐시가 아니라 요청 단위 메모이제이션" → "// 요청 단위 메모이제이션. 요청 끝나면 버려짐"
  용어 훼손:  FLAG — "// 교착 상태 방지" → "// deadlock 방지"
  틀린 주석:  FLAG — 주석은 3회 retry, 코드는 5회 → 코드에 맞춰 수정
  종결 혼용:  FLAG — 한 파일에 "~한다"와 "~함" 혼재 → 코드베이스 다수 스타일로 파일 내 통일
  용어 보존:  OK — deadlock, fallback 영문 원형 유지 확인
  수정안: [삭제할 주석 목록 + 고쳐 쓸 주석의 재작성]
```

## 과교정 방지 (anti-overfitting)

- 규칙이 주석을 더 나쁘게 만들면 규칙을 어긴다. **정신이 조문을 이긴다.**
- 주석을 억지로 늘리지 않는다. 자명한 코드에 주석 0개가 정답인 경우가 대부분이다.
- 짧게 만들려고 필요한 맥락(도메인 규칙, 경고)을 자르지 않는다. 근거와 결론을 두 문장으로 끊는 것은 평탄화가 아니라 정상이다.

최종 테스트: **이 주석, 옆자리 동료가 달았다고 해도 믿기는가?**
